# 전자혀 안드로이드 출시 (1단계) — 설계

- 작성일: 2026-11-17
- 대상 코드: `cook/` (전자혀 단일 파일 PWA, 기획서 `cook/docs/PRD.md`)
- 상태: 승인 대기 (사용자 답변 반영본)

## 1. 의도와 이유

전자혀를 **구글 플레이에 정식 앱으로 출시**한다.

- **쓰는 사람:** 요리 초보. 맛을 감으로 못 맞추는 사람.
- **쓰는 순간:** 장보기 전. "오늘 기름떡볶이맛 땡긴다"는 생각에서 출발한다.
- **앱을 닫을 때 손에 남아야 하는 것:** **살 재료 목록**.
- **수익:** 1단계는 앱을 전부 무료로 두고, 살 재료 목록의 **쇼핑 제휴 링크** 수수료로 번다. 2단계(이번 범위 밖)에서 프리미엄 1회 구매를 더한다.
- **현재 상황 (사용자 답변):** 쿠팡 파트너스 계정이 **아직 없다.** 구글 플레이 개발자 계정은 **개인 계정**이다.
- **플랫폼 순서:** 안드로이드 먼저. 아이폰은 2단계와 함께 간다.

## 2. 목표 / 비목표 / 반목표

**목표**
1. 맛 이름을 고르면 대표 요리를 고를 수 있고, 그 요리의 **주재료 + 양념**이 앱 하나뿐인 **장바구니**에 담긴다.
2. 장바구니의 각 재료에 쇼핑몰 구매 버튼이 붙는다. 출시 시점에는 **수수료 없는 일반 검색 링크**로 시작하고, 제휴 계정이 승인되면 설정만 바꿔 제휴 링크로 전환한다.
3. 집에 있는 재료는 "집에 있어요"로 체크하면 다음부터 목록 아래로 빠진다. 체크는 기기에 저장된다.
4. Capacitor로 감싼 안드로이드 앱(AAB)을 비공개 테스트 트랙에 올린다.
5. 테스터 12명이 14일 동안 비공개 테스트를 마친 뒤 프로덕션 출시를 신청한다.
6. 구글 플레이 정책과 국내법상 문제가 될 표현(유명인 이름)을 출시 전에 없앤다.

**비목표 (이번 범위에서 하지 않음)**
- 프리미엄 결제(2단계), 아이폰 빌드
- 회원가입, 서버, 클라우드 동기화. 모든 데이터는 지금처럼 기기 안(localStorage)에만 둔다.
- 기존 g 배합 계산 엔진의 수치 변경. 출력이 바뀌면 안 된다.
- 광고 SDK

**반목표 (돌아가더라도 이러면 실패)**
- 초보가 첫 화면에서 막히는 것: 로그인 요구, 잠긴 기능, 광고 팝업
- 제휴 링크가 목록을 덮어서 "사라고 등 떠미는 앱"처럼 보이는 것. 목록이 주인공이고 구매 버튼은 보조다.
- 수수료 고지 문구 없이 제휴 링크를 노출하는 것 (공정위 추천·보증 심사지침 위반)
- 인터넷이 없으면 앱이 안 열리는 것. 계산·목록은 오프라인에서도 돼야 하고, 구매 버튼만 인터넷이 필요하다.

## 3. 제약

- **구글 플레이 개인 계정 (확정):** 프로덕션 출시 전에 **12명 이상 · 14일 연속 비공개 테스트**가 필수다. 일정에 최소 2주 이상을 잡는다. 테스터는 사용자가 모은다.
- **비용:** 구글 플레이 개발자 등록비는 1회 25달러다.
- **제휴 프로그램:** 쿠팡 파트너스 계정이 없으므로 1단계 출시는 일반 검색 링크로 한다. 사용자가 계정을 신청하고, 승인과 앱 내 사용 허용을 약관으로 확인한 뒤 링크를 바꾼다. 그래서 앱은 **링크 만드는 규칙을 코드 한 곳(설정 상수)에서 바꿀 수 있게** 만든다. 이 전환은 앱 업데이트 한 번으로 끝나야 한다.
- **유명인 이름:** 퍼블리시티권(부정경쟁방지법, 2022 시행)과 스토어 지식재산 정책 위험이 있으므로 앱 노출 문구에서 실존 인물 이름을 없앤다.
- **기존 구조 유지:** `cook/`은 빌드 도구 없는 단일 `index.html` PWA다. 웹(PWA) 버전도 계속 같은 파일로 동작해야 한다. 앱 전용 기능은 Capacitor가 있을 때만 켜지게 한다.
- **개인정보:** 수집하는 개인정보는 없지만, 개인정보처리방침 URL과 플레이 "데이터 보안" 양식은 필수다.

## 4. 접근 방법 (검토한 대안)

| 방법 | 내용 | 판단 |
|---|---|---|
| **A. Capacitor로 감싸기** ✅ 선택 | `cook/index.html`을 그대로 네이티브 셸에 넣고 공유·진동 등 플러그인만 더한다 | `miri/`에서 이미 쓴 방식이다. 오프라인으로 동작하고 웹·앱 코드가 하나로 유지된다. 아이폰과 2단계 결제도 같은 길로 이어진다. |
| B. TWA (호스팅된 웹 감싸기) | 웹사이트를 크롬으로 띄우는 얇은 앱 | 호스팅·도메인이 필요하고 첫 실행에 인터넷이 필요하다. 아이폰에서는 못 쓴다. |
| C. React Native로 재작성 | 1,800줄을 앱 전용 코드로 다시 짠다 | 몇 주가 더 걸리고 출시만 늦어진다. |

**사용자가 A를 선택했다.** 이유: 가장 빨리 테스터에게 보낼 수 있고, 이후 단계(아이폰·프리미엄)까지 같은 길로 이어진다.

## 5. 결정된 것 (대화에서 정해짐)

### 5.1 살 재료 목록 = 하나의 장바구니 (핵심 기능, 사용자 승인)
- **흐름:** 맛 이름(감성 탭 카드 또는 계산 탭 맛 스타일) → **대표 요리 2~3개 중 선택** → 인분 선택 → 장바구니에 담기.
- **장바구니는 하나:** 요리를 고를 때마다 재료가 같은 장바구니에 쌓이고, 같은 재료는 한 줄로 합친다. 앱을 닫아도 기기에 저장되어 마트에서 다시 열면 그대로 있다.
- **식단 탭과 합치기:** 식단 탭의 "이번 주 장보기"도 따로 두지 않고 이 장바구니로 보낸다. 장바구니에서 재료가 어느 요리에서 왔는지 작게 표시한다.
- **냉장 탭과 연결:** 냉장 탭에 등록된 재료는 자동으로 "집에 있음"으로 처리한다.
- **산 것 지우기:** 마트에서 산 재료는 체크해서 장바구니에서 지운다. 비우기 버튼도 둔다.
- **목록 범위:** 주재료(떡·대파·밥 등)와 양념을 모두 넣는다. 양념 양은 기존 계산 엔진(`calcRecipe`)의 g 결과를 그대로 쓴다.
- **"집에 있어요":** 재료마다 체크 박스를 둔다. 체크한 재료는 목록 아래 "집에 있음" 줄로 내려가고 구매 버튼이 사라진다. 체크 상태는 재료 단위로 기억해서 다른 요리 목록에도 적용한다(간장을 한 번 체크하면 어디서든 집에 있음).
- **구매 버튼:** 재료 옆 `[구매 →]`. 기기의 외부 브라우저나 쇼핑 앱으로 연다(앱 안 웹뷰로 열지 않음).
- **수수료 고지:** 제휴 링크로 바뀐 뒤부터 목록 상단에 늘 보이게 표시한다. 일반 검색 링크 단계에서는 표시하지 않는다(받는 수수료가 없으므로).
- 화면 예시:

```
🛒 기름떡볶이 · 2인분          수수료 안내 ⓘ
 떡볶이 떡 400g     [구매 →]
 대파 1대           [구매 →]
 고춧가루           [구매 →]  □ 집에 있어요
 ─ 집에 있음: 간장, 설탕, 식용유
```

### 5.2 출시 준비
- **유명인 이름 제거:** 맛 스타일 5개의 이름을 바꾼다. 내부 id(`baek_jongwon` 등)는 저장 데이터 호환을 위해 그대로 둔다.
  - `baek_jongwon` 백종원식 대중 한식, `ryu_sooyoung` 류수영식 원팬 집밥, `lee_yeonbok` 이연복식 중식풍, `choi_kangrok` 최강록식 섬세한 감칠맛, `gordon_ramsay` 고든 램지식 서양식
  - 레시피 팁 안의 "이연복 셰프 스타일" 문구도 바꾼다.
- **상호 표현:** 레시피 이름·설명의 업체명("엽기떡볶이", "마켓컬리에서 인기")은 "~스타일"이나 일반 표현으로 바꾼다. 소스 탭에서 실제 제품을 추천하는 제품명(예: "삼양 불닭소스")은 구매 안내 목적이므로 그대로 둔다.
- **개인정보처리방침:** "수집하는 개인정보 없음, 데이터는 기기에만 저장, 구매 버튼은 외부 쇼핑몰로 이동" 취지의 페이지를 만들고, 공개 URL로 게시한다.
- **앱다운 기능:** 살 재료 목록 **공유하기**(카톡 등으로 보내기)를 네이티브 공유로 넣는다. 장보기 맥락에 가장 쓸모 있는 기능이다.
- **테스터 12명:** 사용자가 지인·요리 초보 커뮤니티에서 모은다. 테스트 기간에 피드백도 받는다.

### 5.3 수익 단계
- 1단계(이번): 무료 + 제휴 링크.
- 2단계(다음): 프리미엄 1회 구매. 이번에는 결제 코드를 넣지 않는다. 다만 나중에 일부 기능을 잠글 수 있도록 기능별 진입점을 한곳에서 관리하면 좋다(빌더 판단).

### 5.4 설계 검토 후 정한 것 (작성자 판단 — 사용자 확인 필요 시 표시)
- **양념 양의 출처 (작성자 판단):** 기존 `RECIPES`를 재사용하는 요리는 레시피에 적힌 양념 양을 그대로 쓴다. 그래야 요리 단계 설명과 목록이 어긋나지 않는다. 새로 쓰는 요리는 연결된 맛 스타일 id와 요리별 카테고리·기준 무게를 데이터에 함께 적고, 그것으로 `calcRecipe`를 호출한다.
- **감성 카드의 시작점 (작성자 판단):** 대표 요리는 맛 스타일 id에 붙인다. 감성 카드는 `sid`가 있는 카드(현재 "요즘 말하는 맛" 10개)만 목록 버튼을 보여준다. 나머지 감성 카드는 지금처럼 시뮬레이터로 간다.
- **수수료 고지 문구 (작성자 판단):** §5.1의 예시 문구 대신, 선택한 제휴 프로그램이 정한 고정 문구가 있으면 그것을 쓴다. 쿠팡 파트너스라면 "이 포스팅은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다."이고, 앱 화면에 맞게 표현을 조정할 수 있는지 약관에서 확인한다.
- **냉장 탭 알림 버튼 (작성자 판단):** 브라우저 알림 API는 앱(WebView) 안에서 동작하지 않으므로 앱 빌드에서는 숨긴다. 네이티브 알림은 이번 범위가 아니다.
- **개인정보처리방침 게시 위치 (작성자 판단):** `cook/`은 GitHub Pages용 구성(`.nojekyll`)이 있으므로 같은 곳에 `cook/privacy.html`로 올린다. 스토어 등록용 개발자 연락처 이메일은 사용자가 정한다.

## 6. 빌더에게 맡기는 것

- Capacitor 프로젝트 위치와 구성 (`cook/` 안에 둘지 등). `miri/`의 `capacitor.config.ts`와 스크립트를 참고한다. `webDir`이 단일 `index.html` + 아이콘·매니페스트를 가리키도록 복사 단계를 둔다.
- 서비스 워커를 앱 안에서 끌지 둘지 (앱 안에서는 캐시가 필요 없고 업데이트 혼선만 생길 수 있다).
- 맛 → 대표 요리 매핑 데이터의 형식과 내용. 기존 `RECIPES` 30개 중 맞는 것은 재사용하고, 없는 요리(예: 기름떡볶이, 파기름 볶음밥)는 주재료 목록만 새로 쓴다. 기존 맛 스타일 23개 전부에 요리를 붙일지, 출시 시점에 일부만 붙일지는 빌더가 정해서 표시한다.
- 재료 이름 → 쇼핑 검색 링크를 만드는 방식(검색어 링크로 단순하게 할지, 상품 단위로 할지).
- 새 이름 후보 (§5.2). 사용자 확인을 받고 확정한다.
- 아이콘·스플래시·스토어 스크린샷 제작 방식.
- 앱 id(예: `com.jeonjahyeo.app`), 버전 규칙, 서명 키 보관 방법. 서명 키는 저장소에 커밋하지 않는다.
- 검증: 기존 계산 결과가 바뀌지 않았는지 확인하는 자동 점검(예: 스타일별 300g 결과 스냅샷 비교), 실제 기기 또는 에뮬레이터 확인.

## 7. 미결 사항

- **쿠팡 파트너스 (출시를 막지 않음):** 사용자가 계정을 신청한다. 승인 후 앱 안 링크 사용이 약관상 허용되는지 확인하고 링크를 전환한다. 허용되지 않으면 다른 제휴처를 고른다.
- **스토어 등록용 연락처 이메일:** 사용자가 정한다 (스토어 등록 단계 전까지).
